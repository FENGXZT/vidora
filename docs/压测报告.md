## 一、结论速览（TL;DR）

| | 优化前 | 优化后 | 提升 |
|---|---|---|---|
| **QPS** | 78.79 | **1158.40** | **14.7×** |
| **平均 RT** | 607.81 ms | **41.31 ms** | **14.7×** |

**修复**：显式配置这两个参数。

## 三、★ 核心发现：AWS SDK 每次签名都在读磁盘

### 3.1 最初的症状

压测只有 **81 QPS，P95 683ms**。一个「从 1 万条数据里取 10 条」的分页查询，
正常应该在几十毫秒量级 —— **600ms 明显不正常**。

### 3.2 第一步：排除数据库

看应用日志（配了 `mybatis.log-impl: StdOutImpl`，每次查库都会打印 SQL）：

```
只有【第一次】请求走了数据库，之后全部命中 Redis 缓存
```

**结论：瓶颈不在 MySQL、也不在连接池** —— 因为 60 秒的压测里，
4900 个请求中只有 1 次访问了数据库。

### 3.3 第二步：一次失败的尝试 —— 独立线程池签名

用方法计时发现 **预签名 URL 是最大的耗时项**，于是尝试"排独立线程并发签名"。

**结果数据很有意思：**

| 指标 | 改动前 | 线程池版 | |
|---|---|---|---|
| 中位 RT | 598 ms | **545 ms** | ✅ 变好 |
| P95 | 683.0 ms | **1443.0 ms** | ❌ 翻倍 |
| QPS | 81.54 | **75.49** | ❌ 下降 |

**「中位数变好 + 尾部爆炸 + 吞吐下降」= 引入排队的教科书特征**：
一部分请求抢到空闲线程（所以快），另一部分在队列里干等（所以极慢）。

**结论：方向错了，回退。**
（预签名若真是 CPU 密集型，那线程数超过核心数就是负收益；
若是 IO 等待型，也别用一个小池子去替换 Tomcat 的 200 个线程。）

### 3.4 第三步：★ 抓线程 dump，找到真凶

压测过程中抓 `jstack`，看**线程到底卡在哪里**：

```
ProfileDisableMultiRegionProvider.resolve                          ← 对应 multiRegionEnabled
ProfileUseArnRegionProvider.resolveUseArnRegion                    ← 对应 useArnRegionEnabled
  └→ ProfileFile.defaultProfileFile()
      └→ ProfileFile.addCredentialsFile()      →  ~/.aws/credentials
      └→ ProfileFile.addConfigFile()           →  ~/.aws/config
          └→ ProfileFileLocation.isReadableRegularFile()           ← ★ 文件系统调用
```

### 3.5 根因

**AWS SDK 的 `S3Configuration` 里有两个参数：**

| 参数 | 作用 |
|---|---|
| `multiRegionEnabled` | 是否启用多区域访问 |
| `useArnRegionEnabled` | 是否使用 ARN 中的区域 |

**如果没有显式配置它们**，SDK 无法确定行为，就会**退化为"去 ProfileFile 里查"** ——
而 `ProfileFile` 的解析会在**每次调用**时：

1. 检查 `~/.aws/config` 和 `~/.aws/credentials` 文件是否存在（`isReadableRegularFile`）
2. 读取并解析这两个 INI 文件
3. 创建大量临时对象（额外 GC 压力）

**一次请求要生成 10 个预签名 URL → 2 个 Provider × 10 次 = 20 次文件系统操作 + 解析。**

在 81 QPS 下就是 **约 1600 次/秒**。

> 💡 这也解释了为什么"单次签名 30ms"不合常理 ——
> **HMAC-SHA256 对几百字节是微秒级的**。那 30ms 里绝大部分根本不是签名，是**读 profile 文件**。

### 3.6 修复

```java
S3Configuration.builder()
        .multiRegionEnabled(false)
        .useArnRegionEnabled(false)
        .pathStyleAccessEnabled(true)      // MinIO 必须
        .build();
```

## 四、★ A/B 交错验证（关键）

**为什么要做**：本机压测受 CPU 状态、电源计划、后台进程影响很大。
**仅凭"改之前慢、改之后快"不足以证明因果关系。**

**方法**：交错执行 **A → B → A → B**

| 轮次 | 时间 | 配置 | QPS（3 次） | 中位数 |
|---|---|---|---|---|
| A₁ | 09-30 22:36 | 未配置（= 停用） | 87.73 / 80.93 / 81.54 | **81.54** |
| B₁ | 10-01 22:48 | **启用** | 1208.31 / 1131.99 / 1153.45 | **1153.45** |
| A₂ | 10-01 23:03 | **停用** | 75.05 / 78.79 / 79.36 | **78.79** |
| B₂ | 10-01 23:08 | **启用** | 1135.64 / 1164.90 / 1158.40 | **1158.40** |

```
A：81.54 → 78.79      （波动 3.4%）
B：1153.45 → 1158.40  （波动 0.4%）
```

**结论：切换配置稳定复现 14.7 倍差异，与环境波动无关。铁证。**

> 📌 **附带结论**：A 组两次（81.54 / 78.79）高度一致，
> 说明**最初那份基线是可信的**，不是环境异常。

### 关于「C. 回退串行」的说明（诚实记录）

把线程池改回串行后，测出 **160.58 QPS** —— 比基线高了近一倍。

**排查结论：这是环境异常，不可复现。**
- 当时电脑 CPU 处于一种特殊的高利用率状态
- 离开电脑一段时间后该状态消失，数字回到 ~80
- 后续 A 组两次（81.54 / 78.79）也证实了 ~80 才是正常水平

**这段数据保留在报告里，因为它本身是一条教训**（见第八节）。

## 六、优化路径复盘

```
① 发现慢：81 QPS / P95 683ms
        ↓
② 看日志排除数据库 —— 只有首次走库，其余命中缓存
        ↓
③ 方法计时 → 定位到「预签名 URL」是最大耗时项
        ↓
④ 尝试线程池并发签名 —— 【失败】
     中位数变好但 P95 翻倍、吞吐下降 → 读出"排队"信号 → 回退
        ↓
⑤ 抓线程 dump —— 找到 real 根因
     ProfileFileLocation.isReadableRegularFile
        ↓
⑥ 显式配置 multiRegionEnabled / useArnRegionEnabled
        ↓
⑦ A/B 交错验证 —— 14.7 倍，稳定复现 ✅
```

**两个关键转折点**：
- **④ 读懂失败的数据**（没有因为"中位数变好"就以为优化成功了）
- **⑤ 用线程 dump 而不是靠猜**（"慢"要先问"线程在干什么"）

## 七、下一步

### 7.1 瓶颈可能已经转移

1153 QPS、P95 只有 63ms —— **分布很紧，说明没有排队**。

要确认新瓶颈在哪，可以把并发从 50 提到 **200 / 500**，看吞吐是否还涨：
- 还涨 → 未到上限，继续找
- 不涨 → 上限在别处（**大概率是 JMeter 客户端**，因为它与服务端同机）

### 7.2 Week 2 互动链路压测（已完成）

> 50 并发，3 次取中位数

| 接口 | QPS | 平均 RT | P90 | P95 | P99 | 错误率 |
|---|---|---|---|---|---|---|
| `GET /video/{id}`（含播放量累加） | **1213** | ~40 ms | 47–49 | 51–53 | 97–112 | 0% |
| `POST+DELETE /video/{id}/like` | **1378**（单端点≈689） | ~35 ms | 50–52 | 57–61 | 75–88 | 0% |
| `POST /video/{id}/comment` | **1597** | ~30 ms | 50–51 | 69–76 | 195–240 | 0% |
| `GET /video?page=1`（对照组） | 1271 | 39 ms | — | 55–58 | 66–70 | 0% |

**★ 关键结论：12~31 个线程即到达吞吐平台**

```
play:    31 线程 → 1231 QPS ｜ 50 线程 → 1246 QPS
comment: 12 线程 → 1616 QPS ｜ 50 线程 → 1652 QPS
```

**瓶颈是单机容量（CPU / 网络），不是代码缺陷** —— 加线程只增加排队延迟。

**成本分布**：MySQL 只占约 13.7 ms，**90% 以上花在应用 / JVM / 序列化 / 同机竞争**。

### 7.3 ★ 游标分页验证（评论列表）—— 本次最有价值的验证

评论列表用**游标分页**（为"无限滚动"设计），核心价值是"**无论翻多深，性能恒定**"。

实测（cursorTime 从首页到约 **144 万条**深度，共 10 档）：

| 深度 | mean RT | P95 |
|---|---|---|
| 首页（0） | 42.1 ms | 57 ms |
| ~11 万条 | 42.3 ms | 57 ms |
| ~129 万条 | 42.2 ms | 56 ms |
| **~144 万条** | **42.6 ms** | **57 ms** |

**10 档深度 mean 极差 1.9%，P95 全部 56–58 ms → 深度零代价** ✅

**顺带量化出一次 MySQL 往返的真实成本：**

| | mean RT |
|---|---|
| 深游标 miss（打 MySQL） | 42.4 ms |
| 深游标 hit（打 Redis） | 28.7 ms |
| **差值** | **13.7 ms** |

> 💡 这是"游标分页值得用"的**直接数据证据** —— 换成 offset 分页，深页会随深度线性劣化。

### 7.4 点赞压测：单行锁竞争确实存在

| 配置 | QPS（单端点） | 平均 RT | P95 |
|---|---|---|---|
| 同 token + 同 video | 731 | 35.4 ms | 74 ms |
| **CSV 多用户 × 多视频** | **880** | **27.1 ms** | **38 ms** |

**+20% QPS，P95 腰斩** —— 同 token 同 video 时 50 线程抢同一行唯一索引，存在单行锁竞争。

### 7.5 优化项验证结果

| 优化项 | 结果 |
|---|---|
| 关掉 `log-impl: StdOutImpl` | 对 play **无效**（+0.4%）；对 comment POST **+16%**、like **+7.7%** 有效 |
| 详情页去掉每请求 2 条 SQL | ✅ 已实施（缓存命中 0 SQL，`isLiked()` 已成死代码） |
| HikariCP 池 30/15 | ❌ **负收益**（play −34%、comment −33%、列表 −63%），但**机理存疑**，待交错复测 |

### 7.6 ⚠️ 压测方法学的问题（**比性能更重要**）

**Week 2 的几组数据是在"整段切换配置"下跑的，存在严重的可比性问题。**

```
009:  comment 2771 / play 2425 / /video 列表 2831   ← 全线 +100%
010:  comment 1859 / play 1591 / /video 列表 1038   ← 回落到比基线还低
```

**而 `GET /video?page=1`（代码在 009 时未被触碰、且实测对是否命中 DB 不敏感）
也同步出现 1030 → 2831 → 1038。**

→ **组间差异主要由「会话环境」主导，不是代码改动。**

**唯一可靠的对比方法是 A/B 交错**（本报告第四节的 14.7× 就是这么得出的）。

**另一处数据污染**：007–010 的 comment POST 共插入 **1,442,206 行**，
**每轮跑在单调变大的表上**（0 → 28 万 → 61 万 → 111 万 → 144 万），越早的轮次越占便宜。

> **结论：以后压 POST 前先清表；比较两个版本必须 A/B 交错，不能整段切换。**

## 八、说明与局限（面试时主动说明）

1. **绝对值不代表生产性能。**
   本机压测（客户端与服务端同机、笔记本硬件、单实例），**只用于自己跟自己比**。

2. **必须做 A/B 交错验证，而不是"改前跑一遍、改后跑一遍"。**
   本机压测受 CPU 状态影响极大 —— 本项目实测**同一份代码曾测出 81 和 160 QPS 两种结果**。
   不交错的对比是无效的。

3. **JVM 应用压测要预热。**
   60 秒的短测里，JIT 可能还没完成热点方法编译。

4. **固定环境**：插电 + 高性能电源计划 + 关闭无关程序。

5. **本次结论的强度**：由于做了 A/B 交错验证且两组内部波动 < 4%，
   **这 14.7 倍是可靠的因果关系，不是环境巧合。**
